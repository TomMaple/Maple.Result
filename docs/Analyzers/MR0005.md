# MR0005: IfSuccess or IfError ignores the value of its function

| Property | Value |
| -------- | ----- |
| **Rule ID** | MR0005 |
| **Title** | IfSuccess or IfError ignores the value of its function |
| **Category** | Usage |
| **Enabled by default** | As warning |
| **Applicable languages** | C# |
| **Code fix** | Yes |

## Cause
A function passed to `IfSuccess`, `IfError`, `IfSuccessAsync` or `IfErrorAsync` returns a value of the type of the result’s value (e.g., an `int` on a `Result<int>`), or a task of it, and the result of the call is used.

## Rule description
In version 2, `IfSuccess` and `IfError` with a function transformed the result: `result.IfSuccess(x => Normalize(x))` returned a result with the normalized value, and `result.IfError(e => Fallback(e))` replaced a failure with the fallback value. Since version 3 they only run side effects: the function runs, its value is ignored, and the call returns the original result. `Then` and `Else` transform.

Such a call still compiles, and the type of the expression is the same in both versions when the function returns the type of the result’s value. This rule reports that case, so that code written for version 2 does not change its meaning without a message. See [Transforming `IfSuccess` and `IfError` renamed to `Then` and `Else`](../migration-v2-to-v3.md#transforming-ifsuccess-and-iferror-renamed-to-then-and-else) in the migration guide.

The rule does not report:

* a function that returns another type, which is a side effect (e.g., `x => builder.Append(x)`, or `x => set.Add(x)` on a `Result<int>`);
* an assignment (e.g., `x => last = x`);
* a lambda with a block body that returns nothing (e.g., `x => { Normalize(x); }`);
* an `async` lambda, or a function that returns a task, passed to the action of `IfSuccess` or `IfError`: [MR0002](MR0002.md) reports it, and names `ThenAsync` or `ElseAsync` when the result of the call is used;
* a call whose result is not used: a statement of its own, awaited or not (e.g., `result.IfSuccess(x => Normalize(x));`).

In `IfSuccessAsync` and `IfErrorAsync`, a lambda with a block body that returns a value is reported too, when the value has the type of the result’s value: a function that returns it in a `ValueTask`, and an `async` lambda that returns it (e.g., `async x => { await Task.Yield(); return x + 1; }`). They bind to the overload for a function that returns a `ValueTask<TValue>`, which awaits the task and ignores its value.

## How to fix violations
* To continue with the value that the function returns, use `Then` for `IfSuccess`, `Else` for `IfError`, `ThenAsync` for `IfSuccessAsync` and `ElseAsync` for `IfErrorAsync`. The code fix renames the method.
* If the function is a side effect that happens to return a value of that type (e.g., `x => count++` on a `Result<int>`), write it with a block body: `x => { count++; }`.

## When to suppress warnings
Suppress a warning of this rule when the function is a side effect and its value is ignored on purpose; a block body says the same without a suppression.

## Suppress a warning
To suppress one violation, disable the rule before the line and restore it after the line.

```csharp
#pragma warning disable MR0005
// The line that the rule reports.
#pragma warning restore MR0005
```

To switch the rule off for a file, a folder or a project, set its severity to `none` in a [configuration file](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/configuration-files) (e.g., `.editorconfig`).

```ini
[*.cs]
dotnet_diagnostic.MR0005.severity = none
```

For more information, see [Configuring the rules](README.md#configuring-the-rules) and [How to suppress code analysis warnings](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/suppress-warnings).

## Examples
### Violations
```csharp
Result<int> ok = Result.FromValue(1);
Task<Result<int>> okTask = Task.FromResult(ok);
int Normalize(int x) => x;
Task<int> NormalizeAsync(int x) => Task.FromResult(x);
int Fallback(Error e) => 0;

// MR0005: normalized is the original result; in version 2 it held the normalized value
var normalized = ok.IfSuccess(x => Normalize(x));

// MR0005: the task is awaited, and its value is ignored
var normalizedAsync = await ok.IfSuccessAsync(x => NormalizeAsync(x));
var normalizedLater = await okTask.IfSuccessAsync(x => Normalize(x));

// MR0005: recovered is the original result; in version 2 a failed result became a success with the fallback value
var recovered = ok.IfError(e => Fallback(e));
```

### Fixes
```csharp
Result<int> ok = Result.FromValue(1);
Task<Result<int>> okTask = Task.FromResult(ok);
StringBuilder builder = new();
HashSet<int> set = new();
int last = 0;
int Normalize(int x) => x;
Task<int> NormalizeAsync(int x) => Task.FromResult(x);
int Fallback(Error e) => 0;

var normalized = ok.Then(x => Normalize(x));
var normalizedAsync = await ok.ThenAsync(x => NormalizeAsync(x));
var normalizedLater = await okTask.ThenAsync(x => Normalize(x));
var recovered = ok.Else(e => Fallback(e));

// Not reported: side effects
var appended = ok.IfSuccess(x => builder.Append(x));
var added = ok.IfSuccess(x => set.Add(x));
var assigned = ok.IfSuccess(x => last = x);
var called = ok.IfSuccess(x => { Normalize(x); });
```
